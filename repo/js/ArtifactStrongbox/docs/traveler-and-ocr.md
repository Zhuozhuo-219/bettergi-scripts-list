# 旅行者七元素与OCR预处理（0.7.1）

更新：2026-10-26。

## 旅行者身份

右侧介绍仍使用已建立的模糊模板匹配：从世界之外漂流而来的旅行者、被神带走血亲、寻找七神等多段证据。满足模板及页面条件后，结合当前左上角元素标题，统一为：

`旅行者（风）/旅行者（岩）/旅行者（雷）/旅行者（草）/旅行者（水）/旅行者（火）/旅行者（冰）`。

空、荧、自定义名字均不拆成不同人物。当前标题中的元素优先于历史字段；当前元素未确认时重试，不根据旧记录猜测。账户可保留多个历史元素分支，但属于同一个旅行者，装备者的同一自定义别名根据本轮已确认元素映射。当前分支未经确认时不会随意选择一个历史分支。

账号记录包含`baseName: 旅行者`、`kind: traveler`、`element`、完整显示名和原始别名。稳定存储键按旅行者及元素生成，不依赖男女或显示格式。培养选择统一为同样的七种显示名；旧“旅行者·元素”名单兼容读取。已有评分库本来包含冰主条件，现补入默认候选列表，总默认分支由126变为127；七种分支均与原评分器逐一对照通过。手工旅行者流派需明确填写元素。

用户提供的`reference-images/自定义名称-旅行者冰.png`已保存，实际OCR读出“冰元素/示例”、旅行者介绍及UID。以原图SHA256、同账号UID、同名别名和元素匹配作为迁移证据，将已存`示例`更正为`旅行者（冰）`，保留原始名字和介绍证据。备份及报告在`data/name-migrations/2026-10-26T14-10-46-113Z/`，角色仍为33条。开发工具`node tools/migrate-account-names.mjs --traveler-reference`仅预览，加`--apply`提交。

## 当前OCR是否做增强

运行链路是：截图 → 按坐标选择ROI → `findMulti(RecognitionObject.Ocr(...))` → BGI OCR引擎 → 名称字典／简介匹配／多帧复核。脚本没有额外执行CLAHE、锐化、放大或二值化。

已核对[BGI ImageRegion实现](https://github.com/babalae/better-genshin-impact/blob/main/BetterGenshinImpact/GameTask/Model/Area/ImageRegion.cs)：普通`FindMulti(Ocr)`把ROI传给`OcrFactory.Paddle.OcrResult`。OCR模型内部的输入处理与脚本额外的对比度增强是不同层次。`UseBinaryMatch`属于模板匹配，不能当成该OCR链路的增强开关。另有单区域颜色筛选OCR分支，但当前脚本没有使用。

## 这张图的实际对照

开发工具`tools/compare-traveler-ocr.py`使用RapidOCR，对同一张图的左上标题、右侧姓名、介绍三处分别测试。原始框、变体输出、预处理耗时与字符编辑距离固定在`tools/fixtures/traveler-ocr-comparison.json`。字符误差忽略标点和空格：

| 方法 | 元素与名字误差 | 介绍误差 |
| --- | --- | --- |
| 原图 | 0 | 0 |
| 灰度＋CLAHE局部对比度 | 0 | 0 |
| 双三次插值放大2倍 | 0 | 0 |
| Otsu二值化 | 0 | 1，出现重复字 |

本机小区域预处理热运行约0.1～1毫秒，首次初始化可能明显更高；耗时主要仍在额外OCR调用。该结果只说明本图原图已足够，不能据此宣称任意角色、任意字体下CLAHE或放大都更好，更不能把开发环境RapidOCR耗时视为BGI耗时。

本版保持原图为默认，没有向BGI运行时加入未经实测的图像增强调用。后续若遇低对比度实际失败图，可在既有的一次重试中，针对姓名／介绍小ROI比较轻度CLAHE或2倍放大，原图结果仍保留并经过字典与身份复核。当前不采用全局二值化覆盖原图。

旅行者七元素、旧名单兼容、装备者别名、多账号隔离及实际图OCR已通过离线回归，尚需BGI游戏内完整测试。
