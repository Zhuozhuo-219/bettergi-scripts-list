## 参考数据的定位

`ArtifactScore` 的角色基础属性、元素、词条需求和特殊分支可以帮助生成候选用途。基础属性与默认词条权重是两类数据：前者是换算数据，后者包含流派和维护者选择。都不直接构成“应该喂掉”的判据。

建议后续把“如何随机强化”与“强化后是否满足用途”分开。前者产生词条结果分布；后者按角色/流派、主词条、套装、充能或其他目标评价每个结果。修改用途权重不应改变强化随机机制。

## 模拟输出什么

当前预测到 +20 的终值分布：主词条换为对应五星 +20 显示值，当前副词条保留；待激活第四条按已识别名称和数值激活，不更改数值，不占一次数值增量。只对剩余数值强化节点抽样。

普通数值强化按四个现有词条等权，各为 25%；这与新生成词条的抽取权重不同。本试行模型进一步显式采用四档增量等概率、各节点独立的假设，界面注明该条件；没有宣称本轮完成了概率实测。四档表已存在，约为最高档的 0.7/0.8/0.9/1.0；取实际档位表数值，不用倍率重建近似值。数据依据见 [miao-plugin extra.js](https://github.com/yoimiya-kokomi/miao-plugin/blob/master/resources/meta-gs/artifact/extra.js) 和 [KQM 档位说明](https://keqingmains.com/misc/artifacts/)。

当前使用固定种子的抽样模拟，默认 N=10000，同一批终值供所有角色评分。相同输入和设置可复现，稳定词条使用缓存；切换候选不改变已有角色的样本结果。0.8.0取消正常预测中的理论最高分计算和输出。

## 遮罩：当前已实现与后续摘要

0.8.0展示 `角色/分支 | 前20%评分 | 前80%评分`，行内标注套装件数、推荐使用率、培养和主词条来源；先四件套使用率降序，再两件套使用率降序，后续来源按分数排序。全部入选规则可滚动查看，移除理论最高分及命中分配。以下“平均分、常见区间、达标概率”保留为将来的可选方案，不与当前两个降序分位混用：

| 项目 | 用户可以如何理解 |
| --- | --- |
| 预计 +20 得分 | 按选定用途和已声明随机模型计算的平均终值 |
| 常见区间 P10～P90 | 中间约 80% 的模型结果范围，表示运气波动，不是理论最低/最高或统计置信区间；离散分布可能覆盖更多概率质量 |
| 达标概率 | 满足选定培养目标的比例，必须同时说明目标是什么 |

达标条件可以是得分阈值，也可以是“充能达到需求且副词条质量达到要求”；未确定目标时，不显示达标概率，也不据此给出素材结论。平均分反映整体水平，区间反映波动，概率回答“值得为这个目标投入吗”。理论极限容易被极小概率结果放大，不作为首屏大数字。

多目标时，仅列最多两个目标摘要。不能把角色 A 的高分、角色 B 的充能约束和角色 C 的概率拼成同一个结果。若统计“至少满足一个目标”，需要对同一终值结果取事件并集，而不是把多个目标概率相加。

还可在后续阶段增加“先升 +4 再观察”的投入建议，但应分别评估激活信息和继续投入的收益；当前不定义阈值或自动操作。

## 是否先收集角色需求

回答“有没有潜在用途”不必先收集完整账号，回答“对这个用户是否值得培养”则需要一些目标信息。角色是否拥有也不等于是否准备培养，完整角色库不一定比用户的培养意图更有用。

建议分阶段增加信息：

1. **通用潜力**：按若干明确用途评估，例如攻击输出、生命输出、防御输出或精通用途；表达潜力，不推断用户不需要的都可作素材。
2. **手选培养目标**：用户选少量角色和玩法，可同时选择未来想培养的角色。角色默认数据帮助填初值，允许覆盖。这是第一版个人化所需的核心输入。
3. **仅补充会改变结论的信息**：选定角色的武器类别、关键命座/流派分支、充能目标和是否接受散件。优先手动选择几个选项；未知条件保留默认或分场景结果，不先开发全账号 OCR。
4. **设置已有装备基准**：用户给每个关心的部位一个目标，或后续手动展示该角色现有装备用于读取。由此才可讨论“超过现有装备的概率”；绝对得分不能自动等于提升率。
5. **按实际使用成本决定是否自动采集**：若手动维护确实频繁，再做用户主动打开资料页的 OCR 导入与确认。记录来源和更新时间，并允许手工修正，避免一次误识别长期影响取舍。

武器和命座不需要在一开始全部收齐。若它们只改变某项需求，优先把最终需求显式化，例如用户直接给充能目标；只有会改变词条用途的分支才展开配置。队伍和循环也可能影响目标，因此读到武器/命座并不能自动得到完整个人需求。

建议下一步先约定“用途得分怎么定义、达标是什么、用户愿意输入哪些目标”，再选择概率模型并做预测器。这样能先得到可解释的胚子潜力，而无需把角色库识别作为前置工程。

## 已实现：已强化次数与剩余节点

`utils/artifact-enhancement.js` 从 `ArtifactScore/utils/artis-score-utils.js` 移植五星四档表和“枚举组合、取最接近显示值”的次数估算。`count` 含初始一次，`upgradeCount = count - 1` 才是额外数值强化，遮罩只为正数显示 `≈N次`，与原脚本角标含义一致。待激活/未可靠解析的行不统计为已经发生的数值强化。

移植时增加当前等级的次数上限、组合缓存和显示取整误差检查。百分比按一位小数、固定值/精通按整数的显示精度检查；无法匹配时不编造次数。一个显示值可能兼容多种次数，因此角标始终带 `≈`；不能把逐条估算直接当作真实强化历史，亦未用它强行反推已强化圣遗物的初始三/四条。

所有已识别的非 +0 等级均使名称变红，并显示当前等级的素材提示，包括 +1、+4、+19 和 +20。切回 +0 或离开详情后清除红名。等级无法解析时提示核对，不当作 +0。

### 从当前等级计数，不能从 +0 重跑

KQM 的机制说明支持五星上限 +20，以及每四级新增或强化词条；本文剩余节点表是由这些节点和当前等级推导的。[机制参考](https://keqingmains.com/misc/artifacts/)

```text
节点集合 = {4, 8, 12, 16, 20}
已过节点 = floor(L / 4)
剩余节点 = 5 - floor(L / 4)          // 0 ≤ L ≤ 20
剩余数值增量次数 = 剩余节点 - 尚需激活的次数
```

| 当前状态 | 剩余节点 | 剩余激活 | 剩余数值增量 |
| --- | ---: | ---: | ---: |
| +0，初始三条，第四条待激活 | 5 | 1 | 4 |
| +0，初始四条 | 5 | 0 | 5 |
| +4，四条生效 | 4 | 0 | 4 |
| +8，四条生效 | 3 | 0 | 3 |
| +12，四条生效 | 2 | 0 | 2 |
| +16，四条生效 | 1 | 0 | 1 |
| +20，四条生效 | 0 | 0 | 0 |

+1～+3 对应 +0 后尚未触发 +4 的节点状态，+5～+7 对应已触发 +4；其余同理。+0 是起点，不是一次随机强化，+20 是终点，也必须包含在输入中。若已到 +4 仍显示待激活，或未读全四条，不正常输出剩余数值增量次数，而是要求核对。+20 后续预测应退化为当前成品值，不再抽样；升级经验暴击也不额外增加上述节点。

模拟时先处理下一个激活节点，再从已有四条里按各 25% 选中一条增加数值。当前按用户确认，灰色预览的名称和数值就是激活输入；不重新生成第四条，也不把其已给定值改成最高档。

## 套装和部位如何缩小用途范围

以下是用户指定的默认筛选策略，不是声称游戏限制散件装备：

- 花、羽：主要查询当前套装的角色/玩法需求，不默认把所有角色都拿来打分；以后可提供用户明确开启的极品散件例外。
- 沙、杯、冠：查询全局主词条相容用途，先展示本套适用角色，再展示少量散件用途。全局泛用指允许作为散件候选，不表示任意主词条都通用。
- 套装匹配作为候选顺序及使用条件，不随意加一段分数把不同用途的分值混在一起。
- 主词条要先匹配用途；角色、流派、套装需求必须属于同一目标。资料缺失或套装未知时输出未覆盖，不能据此判为素材。

为避免“某套只适合固定角色名单”随版本过期，建议将来保存 `套装 → 角色/玩法 → 主词条与需求 → 来源/攻略版本/核验日期`。同一角色的不同玩法拆开；过渡 2+2 和特定命座条件单独记录，不混成一套默认权重。

## 词条组合：查到的依据与拟议规则

### 先区分攻略结论和本项目的保护策略

“双暴＋充能就先别喂”“生命＋充能值得留意”是本项目拟采用的**优先保留复核信号**，不声称攻略给出了统一弃置阈值。可用词条覆盖更广，通常意味着强化命中有用方向的机会更多；但角色不需要该属性时不能算有用。

| 组合/情况 | 拟议处理 | 依据或限制 |
| --- | --- | --- |
| 主词条匹配，暴击率＋暴击伤害＋尚有需求的充能 | 胚子优先保留复核，进入该用途的预测 | 芙宁娜和菲谢尔攻略都先检查充能需求，再考虑双暴；这条保护规则是据此提出的项目策略，不能要求所有角色都如此 |
| 生命需求＋充能需求 | 无双暴也进入对应生命用途复核，不因双暴分低直接丢弃 | 芙宁娜是明确的需求样例；生命与充能可来自主词条或副词条，不能只数副词条 |
| 防御需求＋双暴 | 为防御输出用途保留，不按攻击角色权重判低价值 | 千织攻略明确防御优于攻击，且常见后台玩法不重充能；见上表来源 |
| 精通与攻击、双暴并存 | 先确定反应及角色玩法，再决定各项是否计为有效 | 菲谢尔的精通属于激化等条件用途，不能推广为所有剧团角色的统一需求 |
| 无双暴的治疗/辅助候选 | 不经过统一“双暴必须有”筛子 | 心海常规治疗/辅助不按普通暴击输出培养，是明确反例；[KQM 心海速查，页面标注 Luna V](https://keqingmains.com/q/kokomi-quickguide/) |

上述保护首先针对尚有成长空间的胚子；不能把一个 +20、只有少量初始双暴但大部分强化落在其他词条的成品，仅凭“存在双暴”判为优秀。成品要评价当前有效数值，红名提示其已经投入过资源，两者分别呈现。

### 相互作用不能简化为词条数量

1. **充能存在需求边界**。满足目标循环前应优先考虑，超过需求不再线性等价增伤；芙宁娜的不同队伍、武器及命座会改变需求。没有整套装备与循环时只给低/中/高需求场景，不从单件推断“已经够充能”。[来源](https://keqingmains.com/q/furina-quickguide/)
2. **双暴的配合取决于整套面板**。可暴击伤害的平均暴击乘区包含暴击率与暴击伤害的乘积，因此不应要求每一件都凑成同一比例；已有暴击增益或接近上限时，应降低继续堆暴击率的优先级。[KQM 对整套暴击配比的说明](https://keqingmains.com/misc/artifacts/)
3. **主副词条必须一起看**。同一种属性不能同时作为主副词条，固定生命与生命百分比、固定攻击与攻击百分比是不同类型。暴伤冠带暴击率＋充能，不应因副词条只有“单暴”被拒；生命主词条＋充能副词条也可以满足组合方向。[KQM 词条约束与显示规则](https://keqingmains.com/misc/artifacts/)
4. **有效值应归一化后比较**。建议保留 RV 类的“占该词条最高档比例”作为数值尺度，再按用途赋权；不要把固定生命 209 与暴击率 3.1 直接相加。小生命、小攻击并非普遍绝对无用，但不与相应百分比项混用权重。

### 可实施的评分草案，暂不启用数字阈值

```text
识别完整性和等级检查
  → 套装/部位生成候选用途
  → 对每个用途检查主词条、反应/充能等条件
  → 标记值得保护的词条组合
  → 按剩余节点生成终值分布
  → 对同一用途的各终值计算归一化有效值及达标事件
  → 展示本套优先的最多两个用途与摘要
```

第一版可以采用 `各有效词条的归一化终值 × 用途权重` 的和，同时把充能条件作为单独的达标约束。组合保护负责防止过早排除候选，不先叠一个未经校准的“双暴充能额外加分”，避免和三个有效词条本身的贡献重复计分。双暴乘积和充能缺口在缺少整套面板时按预设场景计算，并注明假设。

仅按用户指定的四条等权模型推导：若四条中有 k 条在当前场景下始终有用，每次数值增量命中该集合的概率为 k/4；独立增量 m 次时，至少命中一次的概率为 `1 - (1 - k/4)^m`。因此双暴加有需求充能的三有效方向通常比仅双暴的两方向更宽，但这不是达标概率；充能达到需求后，有效集合还可能改变。`m` 必须使用剩余**数值增量**次数，不能把激活节点算进去。

当前先不设固定“30 分就留”或“没有双暴就喂”的阈值；阈值要按部位、目标用途、剩余成长空间和用户已有基准另行确定。

## 0.4.0 通用角色评分试行版：实际计算约定

### 评分数据和条件

采用工作区 `ArtifactScore/utils/artis-score-standalone.js` 的本地快照，复制到本脚本 `utils/vendor/miao-score.js`，保留原始数据、评分公式和来源注释；未运行爬虫刷新整个上游库。来源是 [miao-plugin](https://github.com/yoimiya-kokomi/miao-plugin)，包含原脚本的本地覆盖。记录原文件 SHA256、复制日期、修改内容和许可，未虚构缺失的上游提交哈希。

适配仅导出现有内部计算方法，另对诺艾尔单件计算时不存在杯子对象的访问增加可空保护，不修改分数公式。默认扫描 121 个角色条目，其中旅行者拆为快照声明的六种元素，合计 126 个条件候选。角色评分排序不代表该角色一定适合当前套装；本轮通用试行暂不执行此前套装/部位候选限制。

默认条件是 0 命、未指定武器、未指定整套面板、未指定四件套。一个剧团单件不能自动证明已配齐剧团四件套，因此不把当前套装名称强行传作四件套条件。所有词条结果在同一角色条件下评分，不在每次抽样后凭单件数据改写角色整套面板。

### 降序分位的精确定义

```text
对同一角色的 N 个单件评分降序排列：s1 ≥ s2 ≥ ... ≥ sN
前20%评分 = s[ceil(0.20 × N)]
前80%评分 = s[ceil(0.80 × N)]
```

下标从 1 开始，不插值；例如 10 个不同评分取第 2 和第 8 名。前20%是高分侧、前80%是低分侧，不能直接套用常见“升序 P20/P80”的名称和方向。这两个分数来自强化随机性下的经验分布，不是置信区间、实际伤害或账号提升率。

每个最终单件评分按原评分器取一位小数再排序，结果也显示一位小数。使用固定基础种子和语义输入哈希，OCR 框位置、时间戳和空格变化不影响抽样；N 改变后结果可能变化。多个角色使用同一批终值，避免角色之间因随机样本不同而增加比较噪声。

### 主词条和激活处理

- 所有未满级输入的主词条推进到对应五星 +20 显示值；例如生命百分比从当前 7.0% 改为最终 46.6%，而不是拿 +0 主词条计算终值分。
- 现有四条的显示数值作为基值，包括已给定的待激活值。首次激活只改变生效状态，不改写这个值。
- 余下 m 次数值增量中，每次独立选择词条与四档增量。+0 初始三条的 m=4，初始四条的 m=5；中间等级按已过节点扣除。
- +20 的 m=0，只有一个确定的当前结果，三个评分完全相同，也没有新增命中分配。
- OCR 只提供显示精度，当前不恢复隐藏的精确小数；未来增量使用本地四档表。与真实游戏内部小数及数据快照的差异可能造成末位误差。

### 潜在最高分和最优分配

不使用随机样本中的最高分。对 m 次数值增量，独立枚举所有非负整数分配：

```text
n1 + n2 + n3 + n4 = m
终值_i = 当前值_i + ni × 该词条最高档增量
```

m≤5 时最多 56 种分配。每种分配均按同一角色条件评分，保留最高分及各词条的新增命中次数、增量和最终值；待激活值固定，不参与抬高到最高档。若多个方案分数相同，保留一个可行的最优分配，不声称唯一。

该局部单件评分器在**角色条件和主词条固定后**是副词条的非负线性函数，故使用各次最高档再枚举命中分配可得到这个模型的理论上限。它常会把所有剩余命中集中到边际分最高的一项；这是原权重模型的结果，不代表真实伤害下的双暴平衡或充能阈值也应如此。若后续接入随终值变化的条件规则、阈值或非线性伤害模型，须同步改写上限搜索，不能沿用线性结论。

### 不同流派可扩展到什么程度

`assets/character-profiles.json` 可追加条件分支；默认文件为空，自动生成的默认候选仍保留。例如下述只是显式选择现有本地玛薇卡规则的低精通条件，不是自动识别玩家实际面板：

```json
{
  "schemaVersion": 1,
  "profiles": [
    {
      "id": "mavuika-low-em",
      "character": "玛薇卡",
      "label": "低精通条件",
      "options": { "cons": 0, "charAttrs": { "mastery": 20 } }
    }
  ]
}
```

支持 `cons`、`weaponName`、`weaponAffix`、`elem`、`charAttrs` 和 `artisSets`。这些是用户明确提供的固定条件，不从圣遗物词条拼凑成完整配装。`artisSets` 需遵循本地库的条件名称，有些使用简称，不自动做未经核对的映射。

若现有库不含某个玩法，可以在分支添加 `weightOverrides`，覆盖 `hp/atk/def/mastery/recharge/cpct/cdmg/dmg/phy/heal` 的非负相对权重；界面会显示手工分支名称。默认不替用户填造数值。该能力只能改变现有公式下的权重，不能替代完整的天赋、队伍、反应、充能缺口和伤害模型。

本地模块是自动转换产物，部分特殊分支在原文件中回退默认规则，并非每一条上游流派都能完整还原。因此答案是：现有资料足够试行通用单件预测，细分流派和个人需求仍需补充明确条件、经过核验的权重或专门计算逻辑；当前分数不作为自动喂掉依据。

### 输入、缓存和验证

预测前检查部位/主词条类型、单位、数值上界、四条完整性、主副词条互斥与重复、档位匹配，以及累计命中次数能否符合当前等级的初始三/四条预算。+20 主词条必须匹配满级值。异常输入只显示需核对，清空旧表，不继续出似是而非的分数。

首次识别推送计算中；计算完成后，下一轮重新截图、确认仍是同一语义输入才推送结果。计算期间切换到另一件不会立即把旧表贴到新物品上。计算循环定期让出执行并检查取消；重复输入使用缓存。

离线验证覆盖全部 126 默认候选与原单件 API 对照、降序分位方向、56 种分配、16² 完整路径的上限对照、固定激活值、五部位、满级退化、非法累计次数、缓存/取消、手工条件及 HTML 表格清理。在 Node 下以首张截图字段手工录入、默认 N=10000 的一次全库计算约 0.3 秒；这不是 BGI 或真实 OCR 的性能承诺。尚未完成游戏内视觉和性能实测。
